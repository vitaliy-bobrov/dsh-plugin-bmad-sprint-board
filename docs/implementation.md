# Implementation notes

How the board reads a BMAD v7 project: what it resolves, how a ticket is linked
to its plan, and what the bundle is made of.

This is the detail behind [the README](../README.md). Nothing here is needed to
install or use the plugin. The v6 notes this file used to hold are in the
repository history under the `1.0.0` tag's commits.

## The v7 layout it reads

```
_bmad/
  config.toml                 [core] output_folder
  custom/config.toml          team overrides, committed
  custom/config.user.toml     [core] active_initiative, usually not committed
  scripts/resolve_config.py   the tooling's own resolver

<output_folder>/              normally _bmad-output
  initiative-<slug>/
    initiative-<slug>.md      type: initiative, title, status
    tickets/
      tickets.toml            [[epic]] id, slug, title
      epic-<slug>/
        epic-<slug>.md        type: epic, title, parent, status
        tickets/
          tickets.toml        [[entry]] id, type, title, v6_key
          <type>-<slug>-plan.md   title, type, status, ticket
```

`sprint-status.yaml`, `epics.md` and `spec-*.md` are v6 and are not read. A v6
project is detected and refused with a pointer at version 1.0.0.

## Resolving the config

Three TOML layers merge lowest priority first, which is exactly what
`_bmad/scripts/resolve_config.py` does:

1. `_bmad/config.toml`
2. `_bmad/custom/config.toml`
3. `_bmad/custom/config.user.toml`

Only two keys are read: `core.output_folder`, with `{project-root}` reduced to
the workspace root, and `core.active_initiative`.

BMAD's own merge also keys array-of-tables by identity and appends the rest. That
branch is deliberately not reproduced: both keys are scalars, so a later layer
that sets them replaces them. `src/toml.test.js` asserts the merge agrees with
what `resolve_config.py` reports for the repository it runs in, rather than
pinning a literal, so a project that moves its own output folder still passes.

## Linking a plan to a ticket

This is the only place the board interprets rather than reads, so it is worth
being precise. A ticket has two records -- an entry in `tickets.toml` and a plan
file beside it -- and three things can be true:

| Outcome | Rule | Reported as |
|---|---|---|
| **linked by ticket** | the plan's frontmatter `ticket` names the entry id | the ticket's state |
| **linked by name** | the plan has no `ticket`, and its file name is the one BMAD would derive from the entry's title | the ticket's state **and** a gap (L1) |
| **orphan** | nothing claims the file, or the claim is ambiguous | a gap (L3) |

The name match has to tolerate truncation. BMAD derives `<type>-<slug>-plan.md`
from the title when the ticket is created; a title edited afterwards leaves a
shorter stem, so `story-shared-tool-ui-components-valuefield-solveforbutton-resultscard`
belongs to
`story-shared-tool-ui-components-valuefield-solveforbutton-resultscard-formuladisplay`.
Truncation happens before `-plan.md`, so the suffix is stripped from both sides
before they are compared.

A name match is only accepted when **exactly one** plan and **exactly one** entry
could make it. An ambiguous match is left unlinked and reported, because showing
a state that might belong to a different file is worse than showing none.

Linking by name is what makes L1 worth having: `tickets.py` reports a ticket as
unstarted until an entry declares its plan with a `ticket` key, however finished
the plan is.

## Unknown is a state

A v7 story carries no status in `tickets.toml`; the state lives in its plan. A
ticket whose plan is missing therefore has no state at all.

The board does not resolve that to `draft` or to anything else. It counts it as
unknown, gives it its own lane, and reports it (L2). Likewise a status word
outside `STATUS_ORDER` is displayed but never counted as settled (L4) -- guessing
that an unfamiliar word means finished is how a board starts lying.

## Parsing

Two readers, both deliberately small and both documented at their source:

- `src/toml.js` -- tables, `[[array-of-table]]` headers, and scalar values. Not a
  TOML implementation; it covers what BMAD writes. Anything it cannot read is
  skipped, so an unreadable key becomes missing rather than wrong.
- `src/frontmatter.js` -- the `---` fenced blocks on every ticket: quoted and
  unquoted scalars, booleans, numbers, and indented `- item` lists.

Both skip rather than throw. A parser that failed loudly on an unfamiliar line
would take the whole board down over one ticket.

## The bundle layout

```
src/toml.js         src/frontmatter.js
src/config.js       src/store.js        src/model.js
src/detect.js       src/scan.js
src/shell-head.js   src/shell-pre.js    src/shell-post.js

index.js            the Node-facing re-export surface
client.js           GENERATED by build.mjs -- do not edit
build.mjs           inlines src/ into client.js, zero dependencies
```

`build.mjs` inlines each core module in dependency order and strips its imports,
because DSH serves a client bundle as one built file and its loader resolves only
platform seeds. `node build.mjs --check` fails when `client.js` and `src/` have
drifted apart; `src/boundary.test.js` asserts the same thing from inside the test
run so a stale bundle cannot be committed.

`src/boundary.test.js` also holds the line the plugin was built on: the pure
modules name no `ctx`, no DOM, no React and no theme token. That decision decays
silently the moment someone reaches for one, so it is asserted rather than
trusted.

## The core and the shell

| Layer | Modules | Knows about |
|---|---|---|
| Parsers | `toml.js`, `frontmatter.js` | text only |
| Model | `config.js`, `store.js`, `model.js`, `scan.js`, `detect.js` | the file layout; no DSH, no DOM |
| Shell | `shell-*.js` | the sidebar, the theme, React, the workspace face |

The scan takes its file operations as arguments -- `read`, `list`, `stat` -- so
the whole read path is exercised by the tests against a synthetic workspace, with
no Host anywhere in sight.
